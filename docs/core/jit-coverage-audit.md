# Core JIT Coverage Audit

This audit records the baseline JIT acceptance boundary for the `features/jit`
branch. The canonical optimizer artifact remains `LoweredFunction`; the runtime
does not get a new opcode matcher.

## Method

- Enumerate VM handlers that the parser / optimizer can materialize into
  `Instr::op`.
- Compare those handlers with `OP_SPECS` in
  `crates/telomere/src/runtime/jit/backend/ops.rs`.
- Classify each accepted handler by backend lowering path:
  direct native `BaselineOp`, explicit `RuntimeStub`, explicit
  `RuntimeContinuationStub`, or current-op continuation bridge.

At this audit point `OP_SPECS` contains 508 handler entries. The parser refers
to 567 VM handler symbols; 349 parser handler symbols are not direct
`OP_SPECS` entries because many shared/indexed memory, atomic, and SIMD forms
are generated by macro families. Those are covered by the current-op
continuation bridge rather than causing whole-function compile rejection.

## Coverage Classes

- Direct native `BaselineOp`:
  scalar numeric ops, locals, globals, select, refs, traps, control flow, direct
  and indirect calls, default-memory scalar load/store, memory.size/grow, and
  selected optimizer memory/control superinstructions.
- `RuntimeStub`:
  bulk memory, tables, memory wait/notify, selected SIMD stack ops, and guarded
  call fast paths. These now emit a JIT ABI helper call instead of
  `compile.reject.runtime_stub`.
- `RuntimeContinuationStub`:
  branch-heavy guarded memory families, selected SIMD lane/shift/load forms,
  start-call continuations, and other VM handlers that need existing
  `call_next` / `call_code` semantics. These now emit a JIT ABI continuation
  helper instead of `compile.reject.runtime_continuation_stub`.
- Current-op continuation bridge:
  parser/optimizer handlers not listed in `OP_SPECS`, including remaining
  shared/indexed scalar memory forms, atomic load/store/RMW/cmpxchg forms, and
  the broad SIMD arithmetic/conversion/lane-memory families. The bridge calls
  the materialized `Instr::op` pointer from `LoweredFunction`; it does not add a
  runtime opcode matcher.

## Acceptance Contract

An enabled core Wasm opcode should not reject whole-function JIT compilation
only because no direct native shape exists. Direct native code remains the
preferred path, but complex or not-yet-native handlers are accepted through a
JIT ABI helper or continuation bridge.

Before native bytes are placed in the store-local code cache, the JIT now builds
a shared `BaselinePlan` from the materialized `Instr` stream and validates it
fail-closed. The validation boundary checks that `op_lens` covers exactly the
materialized code, decoded JIT ops start on instruction boundaries, branch/table
targets land on instruction boundaries or the lexical end, call operand slots
are in range, and continuation bridges have a well-defined next VM PC. This is a
translation-validation guard for the accepted baseline plan; it is not a formal
proof of target machine-code equivalence.

The continuation bridge installs the existing JIT interpreter stop guard at the
lexical next VM instruction. If the VM handler reaches that next instruction,
control returns to the native baseline stream. If the handler branches, returns,
traps, or creates pending async work, the existing `JitNativeExit` path carries
the continuation/trap/pending state back to the runtime.

Non-opcode rejection remains valid for unsupported targets, disabled JIT,
known-rejected functions, code cache limits, executable-memory allocation, and
machine-code emission failures unrelated to opcode coverage.

## Regression Checks

The JIT integration tests include store-local cache assertions that the runtime
stub, explicit continuation stub, and current-op bridge cases compile into the
JIT cache without adding rejected functions.
