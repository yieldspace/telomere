# WASMの型検査について
## 値の型
wasmには仕様上`i32`,`i64`,`f32`,`f64`と`funcref`,`externref`,`v128`の型がある.
```rust
pub enum ValType {
    I32,
    I64,
    F32,
    F64,
    V128,
    FuncRef,
    ExternRef,
}
```

## 命令の型
wasmの命令はスタック上の値をいくつか消費して,いくつかの値を生成する.
これらの命令の型は実行の前までに決定される.
通常の命令,例えば`i32.add`は`[i32,i32]->[i32]`のような決められた型を持っている.
しかしながら,いくつかの命令は型がコンテキストによって変化する.
その中でも簡単な例は`select`命令であり,これは`[t,t,i32]->[t]`のような型を持つ.
また,`unreachable`は`[a1,a2,a3,...]->[b1,b2,b3,...]`のような型を持つ.
また,他には,`return`や`br`などもコンテキストによって型が変化する.
`return`はその関数が`[a1,a2,a3,...]->[b1,b2,b3,...]`のような型を持つとき`[c1,c2,c3,...,b1,b2,b3,...]->[d1,d2,d3,...]`のような型を持つ.
`br`は対象によってとる型が異なり,`loop`を脱出しようとする場合は`loop`が`[a1,a2,a3,...]->[b1,b2,b3,...]`のような型を持つとき,
`br`は`[c1,c2,c3,...,a1,a2,a3,...]->[d1,d2,d3,...]`のような型を取る(`loop`を対象とする`br`は`continue`のような動作をするため).
それ以外の場合はブロックが`[a1,a2,a3,...]->[b1,b2,b3,...]`のような型を持つとき`[c1,c2,c3,...,b1,b2,b3,...]->[d1,d2,d3,...]`のような型を取る.

## チェッカーの実装
HM型推論の実装では,演算の入出力に,型を割り当てて単一化するなどといったことが良く行われている.
そのような実装をすることも可能ではあるが,より高速に行える方法がある(そのように仕様が定められている).
`unreachable`を適当に処理しながらスタック上の型を追跡するという方法が一般に用いられている.
命令の型を検査する際に,任意の入出力の型として扱える`⊥`という型を導入する.
`unreachable`の型は`⊥`であり,`return`はその関数が`[a1,a2,a3,...]->[b1,b2,b3,...]`のような型を持つとき,`[b1,b2,b3,...]`をとる命令ののちに`unreachable`が来るような命令列と解することができる.ここで問題となるのは,`select`命令であり,`unreachable select`は`[a1,a2,...]-> [b1,b2,b3,...,c1]`のような型を持ち,型がわからない単一の値`c1`をすくなくとも生成するので,これを適切に処理する必要がある(例えば,値を返さないブロックにおいて,`unreachable select`のような命令列が出現した場合,それは有効なプログラムではない).
